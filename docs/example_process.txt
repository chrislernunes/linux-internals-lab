why:
  fork() is clone() without CLONE_VM. The kernel duplicates the
  task_struct, the fd table, and the page tables. Pages themselves
  are copy-on-write, so the byte copy is cheap; the page-table copy
  is not, and it grows with the parent's address space.
  execve() throws that address space away: it loads the ELF, maps the
  dynamic linker, and flushes the TLB. That is why fork+exec is
  several times fork+_exit.
  posix_spawn() is what most runtimes should call instead of fork+exec.
  Modern glibc implements the common case with clone(CLONE_VM|CLONE_VFORK):
  the child borrows the parent's address space until exec, so the page
  tables are not copied, and the parent stays stopped so that sharing
  is safe. The saving is proportional to the parent's page tables. In
  this small process exec dominates, and posix_spawn may only beat
  fork+exec by a little. Allocate a multi-gigabyte buffer in the parent
  and run again if you want the gap to open up. strace -f -e clone,clone3,execve
  shows the flags. Raw clone() from C++ is intentionally not called:
  the child would share or abandon glibc TLS, which corrupts the parent.
  Reaping is a wait queue wakeup inside waitpid. Throughput is the
  inverse of the full create-and-reap latency, not of the syscall alone.
  A large parent (big heap, many threads' stacks) makes fork slower.
  This process is small; do not quote these numbers as 'the' fork cost
  of a fat server.
